# 三创赛常规赛：项目定位、竞品检索与升级建议

检索日期：2026-11-19。研究对象为当前 Vue + Django 农产品电商项目。用户偏好：区域平台规模、软件先行、后续可接硬件、美观大气的科技风界面。本文件是方向研究和产品建议，未实施以下新增功能；案例介绍来自所列来源，场景、价格及试点规模均为建议或假设。

## 1. 推荐定位

建议参加常规赛的“三农电子商务”主题，暂定项目名：**禾链智配——区域农产品产销协同平台**。

一句话介绍：连接合作社、集配中心与城市采购商，把采购需求与真实供货批次匹配起来，协同完成分级报价、集单配送、验收结算和异常补货。

核心定位是面向区域农产品流通组织的协同软件：服务多个供货方和多个采购方，由合作社联合体、产地集配中心或区域流通服务企业运营。首期重点做果蔬，逐步复制到不同区域和适合的品类；肉禽、水产等应单独设计规格、温控和验收流程。

规模体现在多主体、多产地、多采购渠道和可复制的协作规则。早期验证可以只跑通一个区域的一条真实供应链，以便证明机制有效。

### 为什么选这个方向

| 候选方向 | 优势 | 主要问题 | 建议 |
|---|---|---|---|
| 全国综合助农商城 | 容易理解，现有代码复用多 | 与成熟平台同质化，获客和物流要求高 | 交易能力作为基础模块 |
| 农产品溯源平台 | 页面直观，便于演示 | 单独扫码查档案的付费动机弱 | 溯源嵌入采购、验收、争议流程 |
| 农场生产管理系统 | 可接遥感、传感器 | 离电商交易较远，依赖农业作业数据 | 保留为供应侧扩展 |
| 区域产销与履约协同 | 直接覆盖采购效率、履约、损耗和争议 | 需要业务规格、跨主体协作和实测数据 | 推荐主线 |
| 临期/余量果蔬销售 | 有减损价值，适合形成特色 | 单一低价渠道可能限制定位 | 作为平台的分级分渠道能力 |

## 4. 应用场景与产品角色

### 核心客户与付费方

- 合作社联合体/产地集配中心：统一管理多家供货、多个批次和销售渠道，减少电话表格协作。
- 区域流通服务企业：汇集供需、安排履约、进行对账，可作为最直接的付费客户。
- 连锁零售、餐饮采购：集中发布需求，比较到货成本与交付条件，管理多门店签收。
- 农户与普通消费者：分别作为供货参与者与延伸销售渠道，不强制承担复杂的运营职责。

### 三个可演示场景

**场景一：连锁门店集中采购。** 采购员发布次日多门店的品类、规格、重量和到货窗口。平台从多个合作社批次中生成候选方案，展示报价、配送成本、验收条件和替补货源。采购员确认后形成订单、分拣单与配送单。

**场景二：同一批果蔬分级销售。** 合作社录入批次和抽样记录，对可销售商品的外观、尺寸、包装和用途形成不同报价方案。各渠道有独立规格与验收条件，平台建议分配，负责人确认后成交。现有 Rotten 单类模型只能辅助发现疑似腐烂，不能直接承担完整分级。

**场景三：到货异常协同。** 某门店验收发现短重或不符合约定规格，上传照片、称重和争议项。平台追到订单与源头批次，计算待补数量，查询同区域可用货源，生成补货/退货候选及责任处理记录。

这三个场景共享同一套业务数据，能串成完整的答辩演示。

## 5. 三条核心创新主张

以下是待验证的应用与模式创新候选，不是已确认的原创算法或专利结论。

### 创新一：把批次品质和采购用途一起纳入匹配

采购方不仅提交“买什么、多少钱”，还提交规格容差、最低等级、包装、交期和允许的替代条件。供应方以批次提供可售量、质量记录、价格和可发货时间。

先按硬性条件剔除不合格候选，再按到货成本、交期、余量风险和历史履约排序；一个需求可以由多个批次满足，一个批次也可以分配给多个采购方。解释每个推荐方案为什么适合、哪些条件不满足。

首期使用可解释规则与约束分配。有足够真实数据后，再评估引入需求预测或学习排序。不能用合成数据的效果支持实际增收、减损结论。

**验证：** 与人工找货/按价格排序比较，记录采购耗时、匹配成功率、到货成本、履约率和运营人工投入。

### 创新二：将质量证据变为订单验收依据

为每个批次维护数字档案，记录来源、采收/入库、抽样、外观缺陷检查、人工复核、分装、发货、签收等事件。抽样范围、数量和未覆盖项目必须可见。

订单成交时固化规格、价格、交付条件和已确认的质量证据快照。到货出现争议时，对比双方约定和签收证据；追溯页面直接服务采购决策和售后。

遥感作为产区背景资料。图像模型作为可见外观缺陷辅助检查，不能替代食品安全检测。哈希和签名用于识别后续修改，不能单独证明最初填报真实。

**验证：** 记录证据完整率、争议率、处理时长、实际退赔和复购。低争议率不能脱离客户样本和试用周期单独归因于平台。

### 创新三：把周期集单与异常替补连接起来

在截单前汇总需求，按批次、配送区域和到货窗口生成采购与发运方案；截单后仍保留短重、缺货和拒收的补救流程。平台给出可执行的替补货源和成本变化，由相关负责人确认。

特色在于“计划—履约—异常—补救”的连接。采用现有运筹工具并不自动构成算法创新，应突出业务约束设计、协作机制和实测改善。

**验证：** 与原配送方式比较单位履约成本、准时率、缺货恢复时间、损耗与净贡献。没有真实车队数据时只能报告离线仿真结果。

## 7. 当前代码需要先补齐的事实问题

本节基于静态读取代码，不是完整安全或质量审计。

1. `code/system/api/models.py` 的 Order 目前没有独立的数量字段，Product 也没有库存计量单位。采购数量应持久化，订单明细应固化计价单位、单价与金额。
2. `code/system/api/views.py` 的创建订单逻辑按 retail_price 计价，未使用已有阶梯价表；并在创建待付款订单时增加销量。应区分预留库存、实际成交与已完成履约。
3. 同文件的支付接口只是将状态改为 paid，没有支付渠道确认。演示时须标明模拟支付；商业验证的实际收款需有可核对记录。
4. `code/system/train_model.py` 在订单不足时使用随机合成特征与标签。`recommend_service.py` 在模型不可用时使用随机评分。这些是演示回退机制，不能作为预测有效性的证据。
5. 本地 `data.yaml` 只有 `Rotten` 一个类别。完整商品分级还需要等级定义、不同批次数据、抽样规则、测试集、模型与人工复核记录。不能将未检出腐烂自动当成合格或高等级。
6. `code/mock_x5.py` 随机生成设备负载、推理延迟和告警。展示时需要区分模拟与实测，未来接入真实设备后再报告对应性能。
7. `gee_service.py` 当前使用 MODIS NDVI、SMAP 土壤湿度，并在点位周围5公里范围聚合。官方数据目录中，前者为250米产品，后者为约9公里产品。因此目前更适合作为区域背景信息，无法直接证明某批果蔬的质量或某个小地块的精细状态。[MODIS 官方目录](https://developers.google.com/earth-engine/datasets/catalog/MODIS_061_MOD13Q1)，[SMAP 官方目录](https://developers.google.com/earth-engine/datasets/catalog/NASA_SMAP_SPL4SMGP_008)

技术上继续沿用 Vue + Django + MySQL 即可。先扩展清晰的数据模型和业务流程，再按需要添加后台任务、缓存或优化服务；平台规模的表达不要求立刻引入微服务和复杂集群。

## 8. 页面视觉方向

整体方向：**农业供应链的空间感与精密协作感**。以真实产地、批次和物流连接作为视觉主体，保留果蔬、土地与人的行业特征。

| 设计项 | 建议 |
|---|---|
| 主要色板 | 深海军蓝 #0D1B2A、靛蓝 #3157C8、农田绿 #1E8A6A、浅背景 #F3F6FA、主文字 #18263A、警示琥珀 #C57816 |
| 字体 | 中文采用思源黑体/系统中文字体回退；正文14—16px，标题建立清晰层级；数字采用等宽数字特性 |
| 对外首页 | 宽幅产地影像或地图；一句话讲清客户价值；入口为“发布采购”“管理供货”；展示可核实的试点证据 |
| 区域总览 | 深色地图与供需流向作为主视觉；显示区域、时间、品类筛选；侧边展示待处理缺口和履约风险 |
| 业务工作台 | 浅色内容区，清晰表格、过滤、批量操作和详情抽屉；采购员能快速完成工作 |
| 品质档案 | 大图对照、抽样说明、检测与人工记录、事件时间线、订单验收条件 |
| 撮合方案 | 并排比较候选：到货成本、可用量、时间窗、证据完整度、未满足条件 |
| 交互动效 | 确认分配后更新流向，展开批次显示来源与去向；非必要动效可关闭 |
| 诚信表达 | 实时、历史、估算和模拟数据有清晰标识；空数据时引导接入，不显示虚构交易额 |

总览页负责建立规模感，工作台负责操作效率，两者共享品牌和组件规则。首屏的地图必须能点到具体需求、批次和订单，才有业务意义。

## 9. 商业模式与验证路线

优先验证面向集配运营方的年度软件服务费，包含组织、批次、采购、履约、品质档案和经营分析。实际代运营、质检或配送服务可按清晰服务范围另行计价；交易服务费应与可证明的撮合或履约价值对应。

首期优先采用合作模式接入现有仓配资源。自建全国仓网会显著改变项目的资金和运营要求，需要另外论证。

财务模型至少区分商品成交额、平台服务收入、配送收入、商品采购成本、物流、人工、模型/API费用和退赔。**平台净收入不等于GMV。** 定价应通过试用和付费访谈确定，尚无依据给出市场均价。

### 建议的阶段推进

| 阶段 | 交付物 | 可以回答的问题 |
|---|---|---|
| 第一阶段：业务验证 | 供需两端访谈、现有单据和流程、客户付费动机 | 痛点是否真实，运营方是否愿意组织协作 |
| 第二阶段：交易闭环 | 多组织、采购需求、批次、报价、验收、对账 | 能否完成一笔真实且可追溯的业务 |
| 第三阶段：差异能力 | 约束匹配、品质证据、周期集单、异常补货 | 哪个新机制改善了哪个指标 |
| 第四阶段：展示与复制 | 科技风界面、试点报告、另一合作方试用 | 页面与数据是否一致，复制成本是否可控 |
| 后续：算法与设备 | 独立评估的模型、真实设备数据和监测 | 新投入是否产生额外业务收益 |

试点建议先找多个供货主体、一个集配运营方及若干稳定采购方，连续运行数个周期。规模按实际接触资源确定，不把建议数量写成已合作规模。

### 必须保存的证据

- 访谈记录和原始需求，合作方授权或试用确认。
- 原始采购单、报价、批次抽样记录、发货与签收凭证。
- 真实结算和平台收费记录；模拟支付不计为实际营收。
- 按品类、季节、客户类型可比的人工流程基线；报告参与批次数、周期和缺失情况。
- 人工采购与平台采购的耗时、完全履约率、单位履约成本、报损比例、争议处理时间和复购。
- 算法测试的时间划分、批次划分、误差、失败案例与人工复核结果；仿真和实测分别报告。

损耗降低、收入提高、配送节省等百分比均需在试点后计算。余量售出量本身不能证明其原本一定会被浪费。

## 10. 答辩主线

推荐通过同一笔业务演示：采购方提出次日需求；供货方提供多批次；系统给出可解释分配；双方确认质量和交付条件；平台生成集单与配送计划；到货异常触发补货；经营分析显示真实成本与效果。

核心表达可以是：**我们让区域农产品交易从“发布商品、等待购买”，走到“按需求组织批次、按约定完成交付”，并用可核对的证据评估协作效果。**

对已有平台的差异应落在试点客户、适配约束、跨主体流程和可证实的效果上。软件工程、开源组件、现成模型、自研规则与实际运营贡献应分别说明。
